# Deploying FoodDelivery on Render

One Render **web service** serves the API (`/api/...`) and the static frontend
(`Frontend/`) from the same address, plus a managed **PostgreSQL** database.
Same origin means no CORS setup and no API URL to configure.

## Deploy

1. Push this repository to GitHub (it already has `origin` set).
2. In Render: **New → Blueprint**, pick the repository. Render reads `render.yaml`.
3. When prompted, enter `ADMIN_EMAIL` and `ADMIN_PASSWORD` (12+ characters).
   This becomes the first admin login.
4. Apply. On first start the app waits for the database, creates all tables from
   `food_delivery_schema.sql` (only if the database is empty), and creates the admin.
5. After the first successful start, **delete `ADMIN_PASSWORD`** from the service's
   Environment tab. The admin account stays; the variable is no longer needed.

Check: open `https://<your-service>.onrender.com/api/health`. It should report
that PostgreSQL is connected. The site itself is at `/`.

## What `render.yaml` sets up

| Item | Value |
| --- | --- |
| Web service | Node, `cd Backend && npm ci --omit=dev`, then `node server.js` |
| Health check | `/healthz` (does not touch the database) |
| Database | PostgreSQL 18, private network only, wired in as `DATABASE_URL` |
| `JWT_SECRET` | generated by Render (random, 256-bit) |
| Region | `frankfurt` for both. Cannot be changed later, edit before the first deploy if you prefer another |
| Plans | web `0.5c-512mb`, database `0.1c-256mb` (both paid). `plan: free` works for a trial but the web service sleeps when idle and is not suitable for live orders |

## What changed for production

- **Same-origin hosting:** Express serves `Frontend/` and `/api`; unknown `/api/*` returns JSON 404.
- **Startup checks:** in production the app refuses to start with a missing/short/placeholder `JWT_SECRET` or no database config.
- **Security headers + CSP:** scripts only from this origin; inline handlers and `javascript:` URLs are blocked (the four inline `onerror` image handlers were replaced by a delegated handler in `api-config.js`).
- **CORS:** same-origin always allowed; extra origins via `CORS_ORIGINS`. A blocked origin gets no CORS headers instead of a 500.
- **Rate limiting:** 1000 requests / 15 min / IP on `/api`; login: 10 failed attempts / 15 min per IP+email and 100 per IP; register 20 / hour; password change 10 / 15 min.
- **Database errors:** PostgreSQL and connection error text is logged on the server and replaced with a generic message in API responses (error codes are preserved, so existing duplicate-key handling still works).
- **Reliability:** graceful shutdown on `SIGTERM`, request body limit (100 kB), JSON error handler, DB pool and statement timeouts.
- **Reviews:** only customers can post; rating 1-5 validated; an order id must belong to that customer and restaurant.
- **Forgot-password page:** no longer claims a reset link was sent (there is no reset backend).

## Things to verify after the first deploy

1. **Client IP for rate limiting.** `TRUST_PROXY=1` assumes one proxy hop. Render
   community reports vary. If every visitor appears to share one IP (login throttling kicks in
   far too early across different users), raise `TRUST_PROXY` (try `2`, then `3`) and redeploy.
   Login throttling is keyed per IP **and** email so a wrong value cannot lock out everyone,
   but get this right before relying on the IP limits.
2. **Place a test order end to end:** register, browse, checkout (cash), restaurant confirm,
   rider deliver, admin totals. The full flow has not been run against a real database yet.
3. **Create restaurant and rider accounts** from the admin portal (public sign-up only creates customers).

## Known gaps (not fixed here)

- **Placeholder images are missing.** Pages reference `assets/images/restaurants/restaurant-placeholder.jpg`
  and `assets/images/food/food-placeholder.jpg`, but there is no `assets/images` folder in the project.
- **Password reset** needs a backend endpoint and an email service.
- **Cash payments** are recorded as `pending`; confirming cash collection at delivery still needs a
  workflow (see `LAUNCH_PREPARATION.md`).
- **Login tokens live in browser storage.** The CSP reduces the damage an injected script could do,
  but httpOnly cookies would be safer long term.
- **`Backend/uploads/`** holds seven images but nothing uploads to it and Render's disk is wiped on every
  deploy, so do not rely on it for user uploads. Restaurant and food images are stored as URLs.
- **Rate limit counters are in memory.** Fine for one instance; if you scale to several, move them to
  a shared store.
- **Database backups:** check the backup/recovery options of your database plan before taking real orders.
- The dependencies are unchanged, so run `npm audit` and update as part of normal maintenance.
